# Инструкции для агентов-разработчиков

Сначала прочитайте [протокол](docs/protocol.md) и [схему архитектуры](docs/architecture.svg). Они описывают целевую реализацию. Пользовательские сообщения этой адаптации пишите по-русски, обычные длинные тире заменяйте короткими дефисами. Комментарии к коду оставляйте на английском и объясняйте в них только неочевидные причины.

## Принципы

- Ядро только принимает события, группирует их, назначает работу и записывает факты. `kernel/` не делает внешних подключений и не знает названий продуктов. Это проверяет `tests/purity.test.ts`. Новые продукты и способы подключения реализуются плагинами.
- Общей веб-панели нет. Источники, исполнители, каналы и владелец используют API. Панели принадлежат отдельным клиентам. Единственная встроенная страница - форма карточки без скриптов.
- Протокол является контрактом всех плагинов. Перед его изменением сверьте документацию и поведенческие тесты; явно укажите совместимость.
- Текст события является данными. Он не попадает в подсказку и не выбирает агента, каталог или права. Инструкции приходят из доверенных правил.
- Цикл не ждет человека. Вопрос записывается в результат, после чего процесс завершается.
- Зависимостей времени выполнения нет. Используйте встроенные возможности Node 24; не добавляйте `dependencies` в `package.json`.
- Пишите только необходимый сейчас код. Дополнительным блокировкам, повторам и запасным путям нужны основания в реальном инциденте или документации интерфейса.

## Изменения и проверки

Тест пишется до реализации; для ошибки сначала нужен воспроизводящий ее тест. В начале файла тестов укажите предотвращаемые сбои. Не меняйте поведенческие ожидания ради подгонки реализации. При локализации меняются только текстовые ожидания и форматы представления; сценарии, ограничения и проверки полномочий сохраняются.

Должны проходить `npm test`, `npm run typecheck`, `npm run format:check`. Без изменений `kernel/`, `protocol/`, `sim/` можно использовать `npm run test:quick`, который пропускает симуляцию и перебор. Полный `npm test` включает симуляцию с фиксированным seed на 200 000 шагов и ограниченный перебор. При изменениях журнала, сроков или параллельности дополнительно выполните `npm run test:nightly`.

`scripts/ci-scope.sh` определяет объем CI. Чистые документы пропускают проверки в PR; обычный код использует быстрые тесты; изменения ядра и протокола дополнительно запускают симуляцию на 20 000 шагов. Изменения симуляции, зависимостей, CI и неизвестных областей требуют полного набора. В `main` всегда запускается полный набор. Уже выполняющийся запуск не отменяется новым push; ожидающий может быть заменен более новым. Nightly проверяет принудительное завершение, мутации, быстрые тесты и установку на актуальном Node. При добавлении каталогов и чтения документов тестами обновляйте классификацию.

Перед мутационной проверкой докажите, что исходные тесты реально выполняются и проходят. Синтаксическая ошибка не считается обнаруженной логической мутацией; пропущенная мутация означает неуспех. Не расширяйте инфраструктуру проверок без необходимости.

## Работа с сообществом

Старайтесь принимать подходящие внешние PR. Необходимые правки сопровождающий делает в ветке автора с сохранением авторства, не заставляя его многократно повторять изменения. Неподходящий PR закрывается с объяснением. Исправимые Issue сопровождающий решает сам. Используйте `Fixes #номер` и корректную подпись `Co-authored-by` автора сообщения, если его вклад должен быть отмечен.

## Независимое ревью

Изменения `kernel/`, `worker/`, `protocol/`, `host/` перед слиянием проверяет агент, который их не писал. Передайте ему код без выводов автора. Он должен установить, кто еще вызывает измененные функции, есть ли реальные записи запуска внешних программ и встречается ли такая же проблема в других местах. Начинайте ревью после открытия PR; независимые PR проверяются параллельно. Исправляйте обязательные замечания; необоснованные запасные механизмы не добавляйте.

Недопустимы:

- доступ без ключа или с ключом другой роли; подмена источника; доступ токена одного цикла к другому; ответ канала без проверки отвечающего и исходного сообщения;
- попадание недоверенного текста в инструкции или его влияние на агента, каталог и права;
- двойная запись или назначение события, превышение параллельности, потеря неудачной работы, немедленный повтор без задержки или без объединения новых событий того же дела;
- ответ, не возобновляющий нужное дело; повторное применение ответа; одновременное изменение карточки ответом и закрытием;
- повтор бизнес-операций из-за неверного JSON результата;
- потеря готового результата исполнителя, принятие работающего процесса за завершенный, новая сессия вместо продолжения прерванной возобновленной сессии, оставшиеся дочерние процессы после остановки;
- внешние запросы, названия продуктов и интерфейс внутри ядра;
- интерпретация текста карточки как HTML или ответ при простом открытии ссылки;
- нарушение документированного контракта старых плагинов, правил и конфигурации без изменения major-версии.

## Граница ядра и хранения

`decide(view, input, now, environment)` создает только факты. Решение и запись выполняются в одной транзакции; представление читается по индексам, решение удерживает только текущие изменения. `evolve` единолично меняет постоянные проекции, `commit` единолично дописывает журнал. Ядро не читает часы, случайные числа, среду или файлы. Время, правила, главный ключ и запросы приходят из оболочки. `host/http.ts` только преобразует Node-запросы в Request и остается не длиннее 50 строк.

Журнал - источник истины. Нормальный запуск использует сохраненную проекцию с курсором и верхней границей ID. При изменении отпечатка формата проекция перестраивается последовательно из журнала, не меняя старые факты. Проекции и индексы сохраняются в одной транзакции с фактами. `kernel/schema.sql` объявляет столбцы представлений; миграции по версиям не добавляются. Версии правил, ответы и результаты доступны через `why` и `/v1/stream`.

## Плагины и доставка

Встроенные и сторонние плагины имеют единый путь `plugins/<имя>/{agent,channel,source}.ts`; установленный плагин имеет приоритет. Ядро их не импортирует. CLI находится в `cli/`, исполнитель - в `worker/`; не добавляйте другой механизм поиска.

Внешние события содержат только данные. Агент, каталог, права, репозиторий доставки и команда ревью задаются доверенными правилами и `main` проекта. События результата наследуют `hops`; после восьми переходов они записываются, но не назначаются дальше.

Процесс доставки не делает checkout кода PR и не запускает его код, тесты, конфигурацию и hooks. Он формирует текстовый снимок из Git-объектов. Стандартное Codex-ревью игнорирует пользовательские настройки и память и сохраняет read-only sandbox. Очередь, параллельность, счетчики ошибок и уведомления принадлежат сервису, а не отдельному планировщику доставки.

Сохраняйте контракт `ops/delivery.json`, четырех меток и статуса `delivery`; статус ревью и команда проверки могут настраиваться. Решение о Ship находится в Action проекта, используемые Actions закрепляются полным SHA.

Сохраняйте проверки инцидентов: настройки только из `main`; ревью собственных изменений ветки; отсутствие повторного ревью того же проблемного коммита; запрет непрозрачных многородительских слияний и чрезмерных diff; запрет слияния PR только для ревью при частичной очистке меток; сохранение разрешенных конфликтов; запрет допуска по черновым checks; повторная проверка коммита, целевой ветки и `main`; подтвержденное отключение auto-merge; чтение состояния после потерянного ответа о слиянии; проверка Ship и фактической health-версии; учет неопубликованного кода под последующими документами; отсутствие отката завершенной доставки при новом выпуске.

При изменении общего контракта согласуйте код, протокол, примеры, README, INSTALL, SKILL, SECURITY и схему. Ищите старые пути, названия, количества и ограничения. Проектные решения записывайте в протокол и правила сопровождения.

## Область тестирования

Симуляция, перебор, принудительное завершение и мутации выполняются при релевантных изменениях. Скорость симуляции - наблюдение, а не критерий выпуска. Не создавайте отдельное ядро для ускорения. Измеряйте память без нагрузки отдельно от тысячи ожидающих подключений; не подменяйте надежную запись пакетными commit.

Скрипты реальных проверок: `scripts/real-agents.ts`, `scripts/real-protocols.ts`, `scripts/delivery-e2e.ts`. Реальная доставка требует `owner/name --run` и создает и удаляет указанный приватный тестовый репозиторий; запускайте ее только по явному запросу пользователя. Остальные тесты используют временный `AGENT_AUTOLOOP_HOME`, случайные порты и очистку. Feishu тестируется фиктивным CLI, каналы - локальным HTTP-сервисом, уведомления - подставными командами в начале PATH. Не отправляйте реальные сообщения и не запускайте второй слушатель действующего приложения Feishu. `scripts/install-smoke.sh` проверяет установленный из коммита код во временной среде; CI запускает его в Ubuntu и macOS.

## Завершение и выпуск

Работайте наборами изменений с исходным списком задач. Новые необязательные находки переносите в следующий набор. Для выпуска нужны успешные полные и ежедневные проверки, корректные состояния Issue, чистая рабочая копия и удаленные временные ветки. Перед Release весь набор независимо проверяется Codex; найденные ошибки исправляются до выпуска.

Версия существует только в tag, не в файлах. Выберите проверенный реальным запуском коммит, выполните nightly на его полном хеше и только после успеха создавайте tag и описание. Опубликованные tag не перемещайте и не удаляйте. Контракт версий и сроков выпуска: [протокол](docs/protocol.md#section-423).
